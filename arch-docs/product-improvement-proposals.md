# Marks 사용성·독창성·심미성 개선 제안

- 작성일: 2026-09-10
- 상태: 1번 구현 완료(2026-09-10), 2번 구현 완료(2026-09-11), 3번 일부 적용(2026-09-12), 4번 보류(2026-09-12), 5번 범위 조정(2026-09-12). 나머지는 제안 단계.
- 검토 근거: 팝업, 페이지 목록, 설정, 인페이지 컨트롤, 미니맵의 코드와 스타일. 실제 브라우저 사용성 테스트 결과는 아님.
- 관련 문서: [기존 UX/사용성 검토](ux-usability-review.md)

## 방향과 범위

빠르게 하이라이트하는 현재 경험을 바탕으로, 저장한 문장을 다시 찾고 활용하는 흐름을 강화한다. 색상과 미니맵을 확장의 개성을 발전시키는 축으로 삼는다.

검색, 전체 펼치기, 사용자 지정 색상 이름 변경, 복원 실패 표시와 재시도는 이미 구현되어 있다. 아래 제안은 이 기능들에 이어지는 작업이다.

### 결정: 실행 취소는 제외

사용자 검토에 따라 개별 삭제 실행 취소는 작업 후보에서 제외한다. 기존 UX 검토 문서의 실행 취소 제안보다 이 결정을 우선한다.

- 개별 삭제는 원문 자체를 지우지 않는다. 사용자는 해당 문장을 다시 드래그해 하이라이트할 수 있어 실수의 비용이 크지 않다.
- 실행 취소는 삭제 기록과 데이터 복원, 재동기화까지 고려해야 하며 동기화 쓰기 제한에도 부담이 된다.
- 삭제 버튼 개선은 조작 영역과 버튼 동작 정리에 한정한다. 실행 취소 토스트, 복구 이력, 삭제 유예는 추가하지 않는다.
- 팝업 개별 삭제 확인과 인페이지 즉시 삭제를 통일하는 작업도 이번 제안에는 포함하지 않는다.

## 1. 검색 결과에서 문장으로 바로 이동

### 구현 상태 — 완료 (2026-09-10)

- 본문 일치 문장 우선 표시, 나머지 문장 펼치기, 제목만 일치하는 결과의 접힌 표시와 검색 집계를 적용했다.
- 문장 클릭·Enter/Space로 정확히 같은 URL의 탭을 재사용하거나 새 탭을 열어 이동한다. 문장을 드래그해 선택하면 이동하지 않는다.
- 기존 복원 상태 조회와 스크롤 메시지를 사용한다. 응답 대기는 최대 15초이며, 원문에서 찾지 못함·준비 확인 실패·탭 닫힘/주소 변경을 구분한다.
- 이동 모듈은 `shared/highlight-navigation.js`에 있으며 저장 데이터나 동기화 쓰기를 추가하지 않는다.
- 단위 테스트와 Chromium 페이지 목록 E2E에서 검색·펼치기 및 기존 탭/새 탭 이동을 검증했다. Firefox 실기 테스트는 실행하지 않았다.

### 변경 전 상태

`pages-list.js`의 검색은 페이지 제목과 하이라이트 본문을 대상으로 한다. 일치하는 페이지를 찾으면 그 페이지의 모든 하이라이트를 펼친다. 개별 문장은 표시만 하고, 해당 원문 위치로 이동하는 동작은 없다. 팝업에는 이미 하이라이트 위치로 이동하는 기능이 있다.

### 제안

- 검색 결과에서 일치하는 문장을 먼저 보여준다. 같은 페이지의 나머지 문장은 `이 페이지의 다른 표시 12개`처럼 접어서 제공한다.
- 제목만 일치한 페이지도 결과에 남기되, 본문이 일치한 결과와 구분한다.
- 문장을 클릭하면 원문 탭을 열거나 기존 탭을 활용하고 해당 하이라이트로 이동한다.
- `3개 페이지 · 7개 문장 일치`처럼 검색 결과 규모를 보여준다.

### 완료 기준과 유의점

- 검색 → 문장 선택 → 원문 위치 확인이 하나의 흐름으로 이어진다.
- 새 탭에서는 콘텐츠 로딩과 하이라이트 복원이 끝난 뒤 이동한다. 복원되지 않은 문장은 이동 성공으로 처리하지 않는다.
- 제목만 일치하는 경우, 검색 결과가 없는 경우, 늦게 로딩되는 페이지를 구분해 처리한다.
- 기존 팝업 이동과 공용 스크롤 헬퍼를 활용하고, 탭 메시지는 `sendMessageToTab`을 사용한다.

## 2. 페이지와 검색 결과 복사

### 구현 상태 — 완료 (2026-09-11)

- 페이지 카드 오른쪽 위와 검색 결과 요약에 같은 복사 아이콘을 제공한다. 개수는 기존 페이지 정보와 검색 요약에 이미 표시되므로 복사 버튼에서 반복하지 않고, 툴팁과 접근성 이름으로 복사 범위를 설명한다.
- 문장별 복사는 제공하지 않는다. 문장 카드는 읽기와 원문 이동에만 사용해 데스크톱과 좁은 모바일 화면에서 반복 아이콘이 만드는 시각적 소음을 없앤다.
- 페이지별 복사는 해당 페이지의 모든 문장을 원문 위치 순서로 복사한다. 검색 결과 복사는 제목만 일치한 페이지와 펼쳐 본 다른 문장을 제외하고 본문이 일치한 문장만 복사한다.
- 복사 결과는 줄바꿈과 Markdown 특수문자를 처리하고 페이지 제목·링크를 포함한다. 성공은 상태 메시지로, 클립보드 API와 폴백이 모두 실패한 경우는 오류 대화상자로 알린다.
- 복사 동작은 저장 데이터나 동기화 상태를 변경하지 않는다. 공용 클립보드 헬퍼는 설정의 동기화 코드 복사에도 사용한다.

### 변경 전 상태

`pages-list.js`의 내보내기는 전체 데이터를 JSON으로 내려받는 백업 기능이다. 문장을 노트나 글에 옮기는 용도의 출력은 별도로 필요하다.

### 제안

- 페이지별 `Markdown으로 복사`를 제공한다.
- 검색이나 색상 필터로 추린 문장만 복사하는 동작으로 확장한다.
- 문장별 복사는 화면 밀도와 플랫폼 일관성을 위해 제공하지 않는다.
- 출력은 인용문과 페이지 제목·링크를 중심으로 간결하게 구성한다.

예시:

```markdown
## [페이지 제목](https://example.com/article)

> 저장한 첫 번째 하이라이트 문장

> 저장한 두 번째 하이라이트 문장
```

### 완료 기준과 유의점

- 사용자가 복사할 범위를 실행 전에 알 수 있다. 전체 백업과 현재 결과 복사를 구분한다.
- 원문의 줄바꿈과 Markdown 특수문자를 처리해 읽을 수 있는 결과를 만든다.
- 복사 성공·실패를 간단히 알린다.
- 기존 JSON 백업 형식은 유지한다. 복사 때문에 하이라이트 데이터나 동기화 상태를 변경하지 않는다.

## 3. 삭제 버튼과 컨트롤 조작 영역 개선

### 구현 상태 — 일부 적용 (2026-09-12)

- 팝업 삭제 아이콘을 문자 `x`에서 SVG 십자로 바꿨다. 글자는 기준선에 앉아 원 안에서 아래로 치우쳐 보였고, 글꼴 보정값으로는 해결되지 않았다. 아이콘은 원의 내부 영역을 채우므로 고정 크기가 남기던 반 픽셀 치우침도 사라졌다.
- Firefox 팝업에서 스크롤 막대가 삭제 버튼 위에 겹쳐 그려지던 문제를 목록 오른쪽 여백으로 해결했다. 같은 크기의 음수 마진으로 그 폭을 카드에 돌려주어 항목 너비는 그대로다. Chrome도 같은 배치를 쓴다.
- 조작 영역 확대는 적용하지 않았다. 인페이지 컨트롤은 이미 24px이고 터치 환경에서 36px이며, 페이지 목록의 아이콘 버튼은 36px, 복사 버튼은 32px이다. 사용자 검토에서 크기 불편은 보고되지 않았다.
- 버튼 요소 전환과 키보드 동작도 적용하지 않았다. 인페이지 막대는 `mouseup`과 `touchend`로만 나타나므로 키보드만 쓰는 사용자는 막대까지 도달할 수 없다. 선택 바의 버튼을 `<button>`으로 바꾸면 포커스가 원문 선택을 무너뜨릴 위험도 있다. 시작점을 고치는 일은 이 제안의 범위가 아니다.
- 검증은 Firefox 실기 확인과 Chromium 정적 복제 페이지 측정으로 했다. 여백 규칙이 있든 없든 항목 너비는 같았다. 팝업 단위 테스트는 그대로 통과한다.

### 변경 전 상태

팝업의 삭제 버튼은 16px 크기의 `span`이다. 인페이지 컨트롤에도 `div`로 만든 버튼이 있다. 작은 삭제 아이콘과 주변 색상 버튼은 조작 영역과 간격을 함께 검토할 필요가 있다.

### 제안

- 작은 아이콘의 시각적 크기와 실제 클릭 영역을 분리해 조작 영역을 넓힌다.
- 팝업 삭제 버튼은 최소 24px 조작 영역을 검토하고, 터치 환경에서는 더 넉넉한 영역과 간격을 확보한다.
- 삭제 아이콘을 SVG로 통일한다.
- 같은 노드를 수정하는 범위에서 `<button type="button">`, 명확한 이름, 포커스 표시와 기본 키보드 동작을 정리한다.

### 완료 기준과 유의점

- 삭제 영역을 넓혀도 문장 이동이나 색상 선택 영역과 겹치지 않는다.
- 버튼이 포커스를 가져가면서 원문 선택 영역이 사라지지 않도록 확인한다.
- 사이트의 전역 버튼 스타일, 터치 드래그와 고스트 클릭 방지 동작을 함께 확인한다.
- 모든 본문 하이라이트를 탭 순서에 추가하는 등의 전체 키보드 탐색 개편은 별도 범위다.
- 실행 취소와 추가 동기화 쓰기는 도입하지 않는다.

## 4. 색상 이름과 목록 필터 연결

### 구현 상태 — 보류 (2026-09-12)

코드 검토 결과 제안대로는 범위가 커서 보류한다. 다시 꺼낼 때는 아래 우려와 축소 범위를 먼저 확인한다.

- 이름 변경은 분류를 깨지 않는다. 하이라이트는 색상 문자열만 저장하고 팔레트도 색상값을 유일 키로 쓰며, 이름은 `customName`으로 따로 붙는다. 아래 완료 기준의 해당 항목은 이미 구조적으로 충족된다.
- 다만 비교는 소문자화만으로 부족하다. 가져오기 스키마는 `group.color`를 비어 있지 않은 문자열이면 무엇이든 받으므로, `rgb(255, 255, 0)`으로 저장된 문장이 팔레트의 `#FFFF00`과 맞지 않아 `기타`로 떨어진다. 비교 전에 양쪽을 hex로 정규화하거나 스키마에서 hex만 받도록 좁힌다.
- 위험한 쪽은 색상값 수정과 삭제다. 팔레트의 hex를 바꾸거나 색을 지워도 기존 하이라이트는 옛 hex로 남는다. 어느 팔레트 항목에도 속하지 않는 색을 가진 문장이 정상적으로 생기므로, 그 문장을 담을 자리가 없으면 어떤 필터에서도 보이지 않게 된다.
- 기본 5색은 이름을 바꿀 수 없다. 설정 화면의 이름 편집과 저장 로직은 `custom_` 접두사 항목만 다룬다. 프리셋을 쓰려면 기본색 이름 변경이 선행되어야 하고, 그것은 컨텍스트 메뉴 제목, 단축키 드롭다운, 기본 이름 번역, 동기화 설정 형식까지 함께 건드린다.
- 페이지 목록은 팔레트를 전혀 모른다. 색상 조회를 새로 붙여야 하고, 설정에서 이름을 바꾼 뒤 목록에 반영되는 경로도 새로 만들어야 한다.
- 표시 이름 계산 로직은 이미 세 벌 있다. 배경 설정 서비스, 설정 화면, 그리고 색상 버튼 툴팁과 원클릭 아이콘 이름에 쓰이는 `content-scripts/controls.js`의 `colorDisplayName`이다. 네 번째 복제 대신 공용 모듈로 뽑고, 이 세 호출부를 모두 옮긴다. 5번 미니맵 색상 탐색도 같은 이름을 쓴다.
- 구현 난이도의 대부분은 일치 판정이 흩어져 있다는 점이다. 같은 본문 일치 조건이 문장 렌더, 검색 요약 집계, 검색 결과 복사 세 곳에 따로 적혀 있다. 색상 조건을 세 곳에 각각 넣으면 보이는 문장 수와 요약 숫자와 복사 범위가 어긋난다.

축소 범위를 택한다면 다음만 한다. 규모는 작음~중간이다.

- 페이지 목록에 색상 칩 한 줄을 두고 하나만 선택하게 한다. 다중 선택은 넣지 않는다.
- 칩 이름은 지금 있는 것만 쓴다. 기본 5색은 기존 번역 이름, 커스텀 색은 사용자가 붙인 이름이다.
- 팔레트에 없는 색을 가진 문장은 `기타` 칩 하나로 묶는다.
- 필터 상태는 메모리에만 둔다. 새로고침하면 검색어처럼 풀린다.
- 프리셋은 제외한다. 색상 필터를 검색 요약이나 복사 범위와 엮지 않고, 색상만 고른 상태에서는 요약 행과 복사 버튼을 지금처럼 숨긴다.
- 착수 전에 본문 일치 판정을 공용 술어 하나로 합친다.

### 현재 상태

`settings.js`에는 사용자 지정 색상 이름 변경 기능이 있다. 이를 페이지 목록에서 의미별로 모아 보는 경험으로 연결할 수 있다.

### 제안

- 페이지 목록에 색상 필터를 추가하고, 설정에서 정한 이름을 함께 보여준다.
- `핵심 · 질문 · 다시 확인` 같은 선택적 색상·이름 프리셋을 제공한다.
- 필터에는 색상뿐 아니라 텍스트 이름과 선택 표시를 함께 제공한다.
- 검색과 색상 필터를 함께 적용해 특정 주제의 질문만 찾는 식으로 사용할 수 있게 한다.

### 완료 기준과 유의점

- 기존 팔레트와 이름을 사용자 동의 없이 덮어쓰거나 재정렬하지 않는다.
- 이름 변경, 색상값 수정, 팔레트에서 제거된 색상의 기존 하이라이트를 어떻게 표시할지 정한다.
- 저장 데이터의 색상값과 팔레트 식별 관계를 먼저 확인한다. 이름 변경만으로 기존 문장이 분류에서 사라지면 안 된다.
- 필터 조작 자체는 하이라이트 변경이나 동기화 쓰기를 발생시키지 않는다.

## 5. 미니맵으로 표시한 부분 다시 읽기

### 검토 결과 — 범위 조정 (2026-09-12)

코드 검토 결과 이 제안은 비용이 다른 세 갈래다. 한 작업으로 묶지 말고 아래 순서로 나눈다.

- 이전/다음과 순서 표시는 싸다. 마커는 문서 조회 순서대로 쌓이므로 이미 원문 위치 순이고, 화면에 보이는 마커 판정도 스크롤할 때마다 이미 돌고 있다. 새로 정할 것은 현재 순서의 기준 하나다. 화면에 여러 개가 동시에 보이므로 위에서 첫 번째를 현재로 삼고, 하나도 보이지 않으면 바로 위 마커로 둔다. 첫 하이라이트보다 위에 있는 흔한 초기 상태에서는 보이는 마커도 위쪽 마커도 없으므로, 첫 마커를 현재로 삼거나 `0 / N` 상태를 두는 경계 규칙을 함께 정한다.
- 색상만 따라가기는 4번과 무관하게 할 수 있다. 콘텐츠 스크립트는 이미 이름이 붙은 팔레트를 들고 있다. 마커 색은 인라인 스타일이라 `rgb()` 문자열로 읽히므로 `color-core.js`의 변환을 거쳐 팔레트 hex와 맞춘다. 팔레트에서 지워진 색을 가진 하이라이트를 건너뛸지 포함할지는 정해야 한다.
- 겹친 마커 펼치기는 뒤로 미룬다. 지금은 마커를 계산된 픽셀 위치에 얹을 뿐이라 겹침 판정 자체가 없다. 묶음 계산, 새 목록 UI, 그리고 모바일의 첫 터치는 확장이라는 기존 동작과의 충돌이 한꺼번에 따라온다.

착수 전과 착수 중에 지킬 것.

- 스크롤, 리사이즈, 본문 크기 변화 세 콜백이 스로틀 타이머 하나를 공유한다. 한쪽이 대기 중이면 다른 쪽 갱신이 조용히 버려지므로, 순서 표시를 얹기 전에 타이머를 콜백별로 분리한다.
- 스크롤마다 마커 수만큼 `getBoundingClientRect`를 이미 읽는다. 현재 순서 계산은 그 패스 안에 넣고 새 패스를 추가하지 않는다.
- 마커는 리사이즈마다 다시 만들어지므로, 현재 위치는 배열 인덱스가 아니라 그룹 식별자로 기억한다.
- 미니맵 폭은 12px, 모바일 16px, 확장 시 24px이다. 이전/다음 버튼은 막대 안에 들어가지 않으니 막대 바깥 배치를 정한다.
- 키보드 지원은 여기서 싸다. 미니맵은 원문 선택과 무관해서 3번에서 막혔던 포커스 문제가 없다.

권하는 범위는 이전/다음과 순서 표시까지다. 색상 따라가기는 그다음, 겹침 펼치기는 별도 작업으로 둔다.

### 현재 상태

`content-scripts/minimap.js`는 하이라이트 위치, 짧은 미리보기, 클릭 이동과 화면 내 표시 상태를 제공한다. 작은 공간에 마커가 겹칠 때 문장을 골라 읽는 동작은 확장할 여지가 있다.

### 제안

- `이전 / 다음 하이라이트`와 `3 / 12` 같은 현재 순서를 제공한다.
- 겹치는 마커를 선택하면 해당 위치의 문장 목록을 펼쳐 선택하게 한다.
- 특정 색상만 순서대로 따라가는 기능을 추가한다.

긴 글에서 질문으로 표시한 곳만 다시 읽는 경험을 목표로 한다. 차별화 기능을 하나 고른다면 이 작업을 우선한다.

### 완료 기준과 유의점

- 이동 순서는 원문의 위치를 따른다.
- 현재 순서의 기준을 명확히 한다. 수동 스크롤이나 색상 필터 변경 후에도 표시가 모순되지 않아야 한다.
- 마커 미리보기와 선택은 모바일에서도 사용할 수 있어야 한다.
- 스크롤마다 전체 문서 탐색이나 전체 마커 재생성을 추가하지 않도록 비용을 확인한다.
- 미니맵을 끈 사용자의 기존 팝업 이동은 그대로 동작한다.

## 6. 문장이 중심인 보관 목록 디자인

### 현재 상태

`pages-list.html`은 페이지 카드 안에 버튼과 문장 카드를 배치하며, 여러 층에 배경·테두리·그림자가 반복된다. 문장 글자 크기는 12px, 페이지 제목은 14px이다.

### 제안

- 문장 글자 크기와 행간을 늘리고 중첩 테두리를 줄인다.
- 제목·도메인·날짜를 출처 정보로 묶어 문장과의 위계를 정리한다.
- 반복되는 삭제 작업은 보조 메뉴로 옮기고, 문장 읽기와 원문 열기에 시선을 집중시킨다.
- 보라색은 주요 행동과 선택 상태에 집중하고, 하이라이트 색상은 콘텐츠를 구분하는 데 사용한다.
- 여백과 정보 밀도를 조절해 긴 문장도 편하게 읽을 수 있게 한다.

### 완료 기준과 유의점

- 긴 제목, 긴 문장, 많은 하이라이트, 빈 결과를 모두 확인한다.
- 밝은 테마·어두운 테마와 모바일 너비에서 출처와 문장의 구분이 유지된다.
- 메뉴로 이동한 작업도 이름을 보고 찾을 수 있어야 한다.
- 검색 일치 표시와 원래 하이라이트 색상이 혼동되지 않게 한다.

## 7. 하이라이트 가독성과 표현 선택지

### 현재 상태

`styles.css`의 본문 하이라이트는 글자색을 검정으로 강제한다. 사용자 지정 배경색이 어두우면 읽기 어려워질 수 있다.

### 제안

- 먼저 배경색에 맞춘 글자색 선택과 실제 문장을 사용하는 색상 미리보기를 개선한다.
- 후속으로 `형광펜 / 밑줄` 표현 선택지를 검토한다. 밑줄은 원문 분위기를 덜 바꾸고 싶은 사용자를 위한 선택지다.

### 완료 기준과 유의점

- 밝거나 어두운 사용자 지정 색상에서 문장이 읽혀야 한다.
- 페이지 링크, 여러 줄에 걸친 문장, 페이지별 스타일 차이를 확인한다.
- 표시 스타일은 기존 하이라이트의 위치와 복원 기준을 바꾸지 않는다.
- 밑줄 설정을 전체에 적용할지 개별 하이라이트에 저장할지는 구현 전에 결정한다. 후자는 백업과 동기화 형식에 영향을 줄 수 있다.

## 권장 진행 방식

먼저 검색에서 문장 이동, 페이지·검색 결과 복사, 버튼 조작 영역 개선을 각각 독립적인 작업으로 진행한다. 저장한 문장을 찾고 활용하는 흐름을 완성한 뒤 색상 필터와 미니맵 재독 기능을 연결한다.

보관 목록 디자인은 검색·필터·복사 동작이 정해진 뒤 다듬으면 화면을 반복해서 개편하는 일을 줄일 수 있다. 하이라이트 표현은 가독성 개선부터 진행하고 밑줄은 후속 선택지로 둔다.
