# UX/사용성 검토 리포트

- 작성일: 2026-08-29
- 대상 버전: 2.9.1
- 검토 범위: 팝업(`popup.html`/`popup.js`), 설정(`settings.html`/`settings.js`), 페이지 목록(`pages-list.html`/`pages-list.js`), 인페이지 컨트롤(`content-scripts/controls.js`), 미니맵(`content-scripts/minimap.js`), 복원 로직(`content-scripts/content.js`), 컨텍스트 메뉴(`background/context-menu.js`), 로케일(`_locales/`)

## 우선순위 높음

### 1. 복원에 실패한 하이라이트가 조용히 사라짐 — 완료 (#113)

`content-scripts/content.js`의 복원 경로(`processRestoreGroups()` → `restoreQuoteGroups()` / `restoreLegacyGroup()`)에서 quote 셀렉터와 레거시 span 복원이 모두 실패하면 `debugLog`만 남고 사용자에게는 아무 표시가 없었다. 팝업 목록은 스토리지 기준으로 그리기 때문에, 팝업에는 하이라이트가 보이는데 페이지에는 없는 상태가 된다. 사용자 입장에서는 "확장이 고장났다"로 인식되는 가장 흔한 시나리오.

**적용한 것:**
- 팝업 항목에 "이 페이지에서 찾을 수 없음" 표시 + 항목별 **다시 찾기** 버튼. 점프 어피던스(`role="button"`, 탭 포커스)는 제거해서 눌러도 아무 일 없는 상태를 없앴다
- 복원 실패 그룹에 대한 1회 지연 재시도. 늦게 도착하는 콘텐츠(지연 로딩 댓글, 펼쳐진 섹션, 아직 정착 중인 SPA 뷰)를 회수한다
- 페이지가 아직 복원 중이면 팝업은 표시를 **보류**한다. 판단이 안 될 때는 목록을 건드리지 않는 쪽이 기본값

**만들지 않기로 한 것:** "복원 실패 개수를 미니맵 또는 액션 뱃지로 알림"은 폐기한다. 사용자가 그 숫자를 보고 할 수 있는 일이 없다 — 몇 개가 실패했는지 알아도 어느 것인지, 무엇을 해야 하는지가 없으면 불안만 남는다. 개수를 세는 대신 **항목별 상태에 행동 수단을 붙이는** 쪽을 택했다.

지연 재시도는 과거 `bc85b6b`에서 도입했다가 저사양 PC·태블릿 부하 피드백으로 `b743c5d`에서 되돌린 이력이 있다. #111/#112로 복원 패스 비용을 줄인 뒤에야(6배 CPU 스로틀 기준 배치당 1457ms → 112ms) 다시 넣을 수 있었다. `MutationObserver`는 일반적인 페이지 변화에도 복원을 다시 돌리게 되므로 의도적으로 쓰지 않았다.

### 2. 하이라이트 목록에서 해당 위치로 점프가 안 됨 — 팝업은 완료 (#110), 페이지 목록은 남음

팝업의 하이라이트 항목은 클릭하면 해당 하이라이트로 스크롤한다(#110). 팝업이 `scrollToHighlight` 메시지를 보내면 `content.js`의 핸들러가 `content-common.js`의 공용 헬퍼 `scrollToHighlightElement()`를 호출한다. 미니맵의 `MinimapManager.scrollToHighlight()`도 같은 헬퍼를 감싼 것일 뿐이라, **미니맵이 꺼져 있어도 팝업에서의 이동은 동작한다.**

남은 것: 페이지 목록(`pages-list.js`)의 "Open Page"는 여전히 페이지만 열 뿐 특정 하이라이트로 이동하지 못한다.

### 3. 삭제 UX: 인페이지 삭제에 되돌릴 방법이 없음 — 우선순위 내림

이 항목은 처음에 "개별 삭제마다 confirm 모달이 떠서 마찰이 크다"로 적었는데, 코드를 보면 사실이 아니다. 두 경로가 정반대다.

- **인페이지 삭제**(`controls.js`의 delete 버튼 → `content.js`의 `removeHighlight()`): 하이라이트를 클릭하고 x를 누르면 확인 없이 즉시 span이 언랩되고 배경에 `deleteHighlight`가 나간다. 확인도 복구도 없다
- **팝업 목록 삭제**(`popup.js`): confirm 모달이 뜬다

자주 쓰는 경로는 이미 원클릭이고, 마찰이 있는 쪽은 목록을 훑어볼 때만 지나가는 드문 경로다. 그러니 "confirm 제거"는 얻는 게 거의 없다.

**남는 문제는 반대쪽이다.** 되돌리기가 필요한 곳은 인페이지다 — 한 번의 클릭으로 사라지고 복구 수단이 없는 유일한 경로이며, 모바일에서는 색상 버튼 옆의 x를 오터치하기 쉽다(고스트 클릭 가드를 넣었던 이력이 오터치가 실재함을 보여준다).

**개선안:**
- 인페이지 삭제: 삭제 후 undo 토스트. 팝업 목록도 같은 토스트를 쓰고 그때 confirm을 없애면 두 경로가 일관돼진다
- 전체 삭제: 삭제 전 "내보내기" 백업 제안 한 줄 추가 (undo와 무관하므로 별도로 처리)

**비용 주의:** 삭제는 `background/message-router.js`의 `handleDeleteHighlight()`에서 `meta.deletedGroupIds`에 툼스톤을 남기고 클라우드 동기화까지 태운다. 스토리지에 그룹만 되돌려 넣으면 다음 동기화가 다시 지운다. undo는 "그룹 복원 + 툼스톤 제거 + 재동기화"가 한 덩어리여야 한다. 페이지 재적용은 쉽다 — `refreshHighlights` 브로드캐스트가 전체를 다시 칠한다.

하이라이트 하나를 잃는 건 다시 칠할 수 있는 손실인데 비용은 위와 같아서, 원래 매겼던 3순위만큼은 아니다.

### 4. 데스크톱에서 하이라이트까지 2번 클릭 — 완료 (설정 토글, 기본 꺼짐)

선택 → 아이콘 클릭 → 팔레트에서 색 클릭의 2단계 인터랙션. 경쟁 확장 대부분은 선택 즉시 색상 바를 띄우거나 "마지막 사용 색으로 원클릭"을 지원한다. 빈도로만 보면 이 리포트에서 가장 자주 걸리는 마찰이다.

처음 적었던 안("아이콘 클릭 = 마지막 색 즉시 적용, 팔레트는 호버/롱프레스")은 그대로 쓰면 안 됐다. 모바일에 호버가 없어 롱프레스만 남는데 발견 가능성이 사실상 0이고, 지금은 오클릭해도 팔레트만 뜨는 동작이 곧바로 원치 않는 하이라이트가 되기 때문이다.

**적용한 것:**
- **설정 토글 `oneClickHighlightEnabled`, 기본 꺼짐.** 꺼져 있으면 기존 동작이 한 줄도 바뀌지 않는다. `minimapVisible` / `selectionControlsVisible`과 같은 경로(저장·브로드캐스트·sync·클라우드 blob)를 타므로 기기 간에도 따라간다
- 켜면 선택 아이콘 클릭이 **팔레트를 여는 대신 마지막 사용 색으로 즉시 칠한다**. 아이콘에는 그 색의 띠를 그려 무엇이 칠해질지 누르기 전에 보이게 했다
- 마지막 사용 색은 hex 하나(`lastUsedColor`)로 남긴다. 하이라이트를 만들거나(선택 바·컨텍스트 메뉴·단축키·`+` 커스텀 색) 기존 하이라이트의 색을 바꾸면 갱신된다 — 규칙은 "색을 지정한 마지막 행위" 하나다. 세 경로가 모두 `content.js`의 `highlightSelectedText()` / `changeHighlightColor()`를 지나므로 기록 지점도 그 둘뿐이다

**팔레트를 잃지 않는 이유:** 호버도 롱프레스도 쓰지 않는다. 칠한 뒤 그 하이라이트를 클릭하면 이미 있던 색상 바가 뜨고, 거기에 전체 팔레트와 `+`와 삭제 x가 다 있다. 흐름이 "고르고 칠한다"에서 **"칠하고 나서 고친다"**로 바뀔 뿐이라 모바일에서도 색 선택이 그대로 살아 있고, 오터치로 칠해진 하이라이트를 지우는 수단도 같은 자리에 있다(완전한 undo는 3번의 몫).

**색이 사라졌을 때:** 저장된 hex가 현재 팔레트에 없으면(설정에서 개별 삭제, 값 편집, #125의 전체 삭제) 팔레트 첫 색으로 폴백한다. 색 id가 아니라 hex로 저장한 이유가 이것이다 — 팔레트는 hex 중복을 허용하지 않으므로 hex는 그 자체로 유일 키이고, 팔레트에서 사라졌다는 사실이 곧 폴백 조건이 된다. 판정은 `color-core.js`의 `resolveLastUsedColor()`에 있다.

**만들지 않은 것:** "팔레트에서 마지막 사용 색을 맨 앞에 크게" 배치는 폐기한다. 하이라이트할 때마다 팔레트 순서가 바뀌면 색 위치에 대한 근육 기억이 무너지고, 이건 토글을 끈 사용자에게까지 영향을 준다 — 순수 추가를 앞에 둔다는 이 리포트의 기준과도 어긋난다. 마지막 색을 알리는 일은 아이콘의 색 띠가 이미 하고 있다.

단축키(슬롯 1~5)의 발견 가능성은 5번에서 처리했다.

### 5. 온보딩 부재 — 완료

`onInstalled` 시 안내 페이지가 없고 팝업 설명도 한 줄뿐이었다. "텍스트를 드래그하면 아이콘이 나타난다", 컨텍스트 메뉴·단축키의 존재를 처음 사용자가 알 방법이 스토어 설명뿐이었다.

**적용한 것:**
- `onboarding.html` — 하이라이트 만들기, 색 변경·삭제, 컨텍스트 메뉴, 단축키, 미니맵, 목록/백업 6개 항목을 도해와 함께 담은 한 장짜리 가이드. `background/onboarding.js`가 **신규 설치에서만** 탭으로 연다
- 팝업 빈 상태(`#no-highlights`)에 3단계 사용법과 가이드 링크 삽입. 신규 설치에만 닿는 가이드와 달리 여기는 기존 사용자도 본다
- 설정에 "사용법 보기" 항목을 두어 언제든 다시 열 수 있게 함

**주의해서 넣은 것:**
- `onInstalled`는 확장 업데이트와 브라우저 업데이트에서도 발화한다. `details.reason === 'install'` 게이트가 없으면 자동 업데이트마다 모든 기존 사용자에게 탭이 열린다. `tests/onboarding.test.js`가 이 게이트를 회귀로 잡는다
- `scripts/deploy.cjs`의 `filesToCopy`는 수동 목록이라, 루트에 추가한 페이지를 등록하지 않으면 언팩 상태에서만 되고 패키징 빌드에서 404가 난다
- 팝업 안내는 `#no-highlights` **자식**으로 넣어야 한다. `popup.js`가 렌더링마다 컨테이너를 비우고 이 노드만 다시 붙이며, i18n 패스가 `data-i18n` 요소의 `textContent`를 덮어쓰기 때문

**만들지 않은 것:** 스크린샷. 6개 언어 × UI 변경마다 갱신해야 하고, 갱신이 끊기는 순간 문서보다 나쁘다. 인라인 SVG 도해로 대신했다.

## 우선순위 중간

### 6. 인페이지 컨트롤의 키보드/스크린리더 접근성 부재

색상 버튼, 삭제 버튼, 선택 아이콘이 전부 `<div>`이고(`controls.js`) `role`, `tabindex`, `aria-label`이 없어 키보드로는 조작 불가. 팝업의 삭제 버튼도 `<span>`이라 포커스가 가지 않는다.

### 7. 팝업 삭제 버튼이 너무 작음

16×16px에 글자 "x"를 아이콘으로 사용. 최소 24px 히트 영역과 SVG 아이콘 권장. 하이라이트 텍스트가 80자에서 잘리는데 전체 텍스트를 볼 방법(title 툴팁조차)이 없다.

### 8. 페이지 목록 툴바의 위험 버튼 배치

아이콘 전용 버튼 5개가 나란히 있고 "전체 삭제"(휴지통)가 "새로고침" 바로 옆(`pages-list.html` 툴바). 파괴적 액션은 more 메뉴로 옮기거나 간격을 두는 게 안전하다.

### 9. 커스텀 색상 피커에 hex 입력이 없음

HSV 슬라이더와 프리셋만 있어 브랜드 색상 등 정확한 값을 지정할 수 없다. 또한 커스텀 색을 추가해도 바로 적용되지 않고 팔레트에서 다시 클릭해야 한다.

### 10. 단축키 변경 동선

설정 화면이 `chrome://extensions/shortcuts` 주소를 텍스트로만 안내한다. Chrome에서는 `tabs.create`로 해당 페이지를 여는 버튼을 넣을 수 있다(Firefox는 불가하니 분기 필요).

### 11. URL 완전일치 키의 함정

하이라이트가 `tab.url` 전체(쿼리스트링, 트래킹 파라미터, fragment 포함)를 키로 저장되므로, `?utm_source=...`가 붙어 재방문하면 같은 문서인데 하이라이트가 없는 것으로 보인다. 최소한 fragment 제거, 나아가 주요 트래킹 파라미터 정규화 검토 가치가 있다.

### 12. 네이밍 불일치

확장 이름은 "Marks: 텍스트 하이라이터"인데 팝업 제목은 "텍스트 하이라이터". 브랜드 노출을 위해 팝업에도 "Marks" 사용이 일관적이다.

## 잘 되어 있는 부분

- 다크 모드 대응 (`prefers-color-scheme` 기반 토큰)
- 6개 언어 로케일 (en/es/ja/ko/zh/pt)
- 모바일 대응: 컨트롤 터치 드래그, 고스트 클릭 가드, 좌표 클램핑
- 미니맵 내비게이션
- 클라우드 동기화의 "코드 분실 시 복구 불가" 경고
- import 시 덮어쓰기 확인

## 권장 착수 순서

효과 대비 비용 기준: ~~2번(팝업에서 점프)~~ → ~~1번(복원 실패 표시)~~ → ~~5번(온보딩)~~ → ~~4번(원클릭 하이라이트)~~ → **6번+7번(접근성·삭제 버튼)**

2번은 #110, 1번은 #113, 5번과 4번은 이후 작업에서 처리했다.

3번과 4번은 원래 다음 순서였으나 검토 결과 둘 다 서술을 고쳐야 했다 — 3번은 전제가, 4번은 개선안이 틀렸다. 위의 각 항목을 참고. 기존 사용자가 있는 확장이라 **동작을 바꾸는 변경보다 순수 추가를 앞에 두는 것**을 기준으로 삼는다. 4번이 6·7번보다 먼저 들어간 것은 그 기준을 어기지 않는 형태 — 기본 꺼짐 토글 — 를 찾았기 때문이다. 남은 다음 후보는 6·7번(인페이지 컨트롤 접근성, 팝업 삭제 버튼 히트 영역)과 2번의 남은 절반(페이지 목록에서 하이라이트로 점프)이고, 셋 다 기존 동작을 건드리지 않는다.
